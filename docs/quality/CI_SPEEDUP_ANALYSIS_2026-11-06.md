# Ускорение CI без потери качества: анализ (2026-11-06)

Анализ и ход работ по ускорению CI. Первоначальные замеры ниже сняты до изменений. Выполнено: кэш браузера, разделение тестов и порядок Container security (#977); шарды E2E и Visual, скрипт установки пакетов Playwright (#978); пропуск тяжёлых проверок для правок только в документации (#979); автозапуск CI после коммита бота со снимками (#980). Текущее поведение гейтов описано в [`READINESS_AND_SECURITY_GATES.md`](./READINESS_AND_SECURITY_GATES.md). Любое изменение набора проверок делается только после явного «да, делай» от владельца.

## 1. Сколько занимает CI сейчас

Замер по запуску PR 976 (только документация), 2026-11-06, от старта до «Checks»: **11 мин 40 с**. Остальные недавние запуски такие же: 10–12 минут.

| Задача | Время | Что внутри |
|---|---|---|
| Browser E2E | **10 мин 30 с** | 56 файлов тестов, 2 параллельных процесса на одной машине |
| Visual regression | 9 мин 40 с | установка браузера 4 мин 05 с (в соседних задачах того же запуска 20 с), сами тесты 5 мин 07 с |
| Tests & database | 5 мин 35 с | модульные 3 мин 20 с, затем тесты с базой 1 мин 30 с подряд |
| Accessibility | 4 мин 55 с | axe 2 мин 50 с, установка и подготовка 2 мин |
| Container security | 3 мин (стартует только после Quality, Tests и Build, то есть через 5 мин 40 с) | сборка двух образов, сканирование |
| Quality & security | 1 мин 20 с | секреты, аудит зависимостей, документация, lint, typecheck |
| Build | 40 с | |

Общее время равно самой долгой задаче: **Browser E2E (10,5 мин)**, следом Visual (9,7 мин). Всё остальное укладывается внутри них.

Главная потеря времени в реальной работе не одна медленная проверка, а **повторные запуски**. За последние два часа на PR 426 было 6 запусков (две красные, две отменённые, один отменённый на 32 минуты, один зелёный), на PR 425 четыре. Причины, которые видны по истории:
- визуальные эталоны: после правки интерфейса нужен отдельный запуск `update-visual-baselines.yml`, коммит бота не запускает CI сам, поэтому потом нужен ещё один полный круг;
- нестабильные места: тест перетаскивания с клавиатуры в редакторе групп (`checklist-groups-dnd.spec.ts`), единичные падения «Tests & database», задержка реестра при установке `playwright-core` в Container security;
- любой пуш отменяет идущий запуск, а merge main в ветку запускает всё заново.

## 2. Что можно ускорить и почему качество не падает

Принцип: те же тесты, те же сканеры, те же пороги. Меняется только то, как они разложены по машинам и что повторяется.

| # | Что сделать | Выигрыш | Почему проверок не меньше | Риск |
|---|---|---|---|---|
| A | **Browser E2E на 3 части** (`playwright test --shard=1/3` и т.д., три задачи рядом) | 10,5 → около 4–5 мин | Выполняются все те же тесты, ни один не пропущен; «Checks» требует все три части | Каждая часть заново собирает API и ставит браузер (около 1 мин), общее машинное время вырастет на 20–30% |
| B | **Visual regression на 2 части + кэш браузера Playwright** | 9,7 → около 3–4 мин; исчезает разброс 20 с…4 мин | Те же снимки и те же допуски | Эталоны не меняются; нужно убедиться, что число снимков сходится |
| C | **Кэш `~/.cache/ms-playwright`** по версии Playwright в E2E, Visual, Accessibility | 20 с…4 мин на задачу, плюс стабильность | Браузер той же версии | Системные пакеты (`--with-deps`) по-прежнему ставятся |
| D | **Container security не ждёт Quality и Tests**, только Build | убирает «хвост» в 3 мин после тестов; после A и B станет критическим путём | Сборка и сканирование те же; требуется Build | Не пропустить: Checks всё равно ждёт все задачи |
| E | **Tests & database на 2 задачи** (модульные и тесты с базой рядом) | 5,5 → около 3,5 мин | Те же тесты | Малый |
| F | **Правки только в `docs/` и `*.md` не гоняют тяжёлые задачи** (Quality & security с проверкой документации идёт всегда) | PR вроде #976: 11,7 → около 2 мин | Код не менялся, проверки кода нечего проверять; проверки документации, секретов и политик остаются | Нужен точный фильтр: любой файл вне `docs/` и `*.md` включает всё; «Checks» допускает пропуск только в этом случае |
| G | **Меньше повторных запусков**: чинить нестабильные тесты по причине, а не перезапуском; запуск CI после коммита бота эталонов без ручного шага | самое большое выигрыш по реальному времени от «кода до зелёного», 2–4 круга по 11 мин на PR | Ничего не ослабляется | Для автозапуска после коммита бота нужен токен приложения GitHub (решение владельца по безопасности) |

Ожидаемый итог при A+B+C+D+E: обычный PR **около 6 минут вместо 11,7**, PR с одной документацией **около 2 минут**. Реальное время до слияния сокращается ещё сильнее за счёт G.

## 3. Что трогать нельзя

Не снижать и не пропускать ради скорости: секрет-сканирование, аудит зависимостей, CodeQL, сканирование образов, axe, визуальные допуски, число тестов, `retries: 0` (ошибка должна быть видна). Не включать повторные попытки, которые прячут нестабильность. Не пропускать проверки для кода «по размеру» изменения.

## 4. Как проверить, что ничего не потеряно

1. До и после на одном и том же коммите: сумма тестов по частям равна числу до разбиения (`playwright test --list`), число визуальных снимков и axe-страниц то же.
2. Намеренно сломать тест и убедиться, что красной станет именно его часть и «Checks» покраснеет.
3. Политика репозитория (`Validate repository governance policy`, контрактные тесты релизных ворот) перечисляет обязательные задачи: обновить её вместе с новыми именами задач, чтобы набор обязательных проверок не уменьшился.
4. Для F: PR с кодом и документацией вместе запускает всё; PR только с документацией пропускает тяжёлые задачи, «Checks» зелёный.

## 5. Предлагаемый порядок (по одному PR в `.github`, каждый только по «да, делай»)

1. **C + D + E** (кэш браузера, Container security после Build, разбиение тестов): без изменения набора тестов, безопасно.
2. **A + B** (разбиение E2E и Visual на части).
3. **F** (пропуск тяжёлых задач при правках только документации).
4. **G**: разбор нестабильных тестов отдельными PR; автозапуск CI после эталонов по решению владельца.

## 7. Уточнения после разбора вторым ревьюером (2026-11-06) и решения по плану

- **C+D+E первым этапом, затем A+B, F отдельно:** принято. При разделении unit/DB сохраняются coverage, smoke-проверки и все обязательные зависимости «Checks».
- **A+B:** «Checks» требует успеха каждой части; отчёты и артефакты частей получают разные имена (с номером части).
- **F строже:** в `docs/` лежат не только Markdown (140 `.md`, 41 `.html`, 4 `.json`, `.gitkeep`). Пропуск тяжёлых задач разрешается только по закрытому списку путей: `docs/**/*.md` и корневые описательные `*.md` (`README.md`, `AGENTS.md`, `CLAUDE.md`, `apps/e2e/**/README.md`, `infra/railway/README.md`, `scripts/SMOKE.md`, `services/malware-scanner/README.md`, шаблоны `.github/*.md`). Любой другой путь, в том числе `docs/**/*.html` и `docs/**/*.json`, и любой неизвестный файл запускают полный CI.
- **Кэш Playwright:** он не убирает установку системных пакетов (`--with-deps`), поэтому задержки могут остаться; ключ кэша включает ОС, архитектуру и версию браузера. Эффект измеряется, а не обещается.
- **«6 минут вместо 11,7» это прогноз.** В последнем зелёном запуске сами E2E заняли около 9 минут (в PR 976 10,5), визуальные около 6. После разделения время замеряется на нескольких запусках и записывается сюда.
- **G:** кроме токена приложения GitHub для запуска CI после коммита бота есть вариант с явным `workflow_dispatch` (отдельный запуск CI на ветке по нажатию или из workflow эталонов); сравнить при реализации.
