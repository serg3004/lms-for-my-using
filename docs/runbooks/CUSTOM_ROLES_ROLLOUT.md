# Индивидуальные роли: включение и откат по организации

> **Статус:** `CURRENT PROCEDURE` (PR 486). Выключатель `Organization.customRolesEnabled` по умолчанию выключен. Пока он выключен, права проверяются только встроенными политиками, как до PR 481.

## Что считается состоянием

- Роли, их права и назначения лежат в таблицах `custom_roles`, `custom_role_permissions`, `user_custom_role_assignments` (миграция `20261119150000_custom_roles`, описание в `MIGRATION_BACKUP_POLICY.md`).
- Что действует сейчас, решает только значение `organizations.custom_roles_enabled` и состояние роли (`active`) и назначения (`active`). Кеша между запросами нет: отзыв роли, архивирование и выключатель действуют со следующего запроса, без нового входа.
- Управление ролями (`/custom-roles`) всегда остаётся у администратора и от выключателя не зависит.

## Включение

1. Убедиться, что на нужный SHA пройден CI (включая `custom-roles-*.database.spec.ts` и `custom-roles.acceptance.spec.ts`).
2. Администратор организации: «Администрирование → Роли и права → Включить» (или `PATCH /organizations/{id}/features` с `{ "longreadEnabled": <как было>, "customRolesEnabled": true }`).
3. Создать роль «на пробу», назначить тестовому сотруднику, проверить из его сессии: новые возможности появились (`GET /me/permissions`, экран), лишнего нет.
4. Снять роль и убедиться, что возможности исчезли без повторного входа.

## Откат

Откат возвращает встроенные политики и ничего не удаляет.

1. Выключить переключатель тем же экраном или `PATCH /organizations/{id}/features` с `"customRolesEnabled": false`. Действует со следующего запроса.
2. Если администратору недоступен экран, аварийно, одной командой на нужной базе (идентификатор организации подставить из таблицы `organizations`):

   ```sql
   UPDATE organizations SET custom_roles_enabled = false WHERE id = '<organization-id>';
   ```

3. Проверить: сотрудник с пользовательской ролью получает на её маршрутах 403, встроенные роли работают как раньше, `GET /me/permissions` показывает `customRolesEnabled: false`.
4. Роли и назначения остаются в базе. Повторное включение возвращает их без пересоздания. Таблицы не удалять и миграцию не откатывать: определения ролей и назначения будут потеряны.
5. Пользовательская роль не превращается во встроенную. Если сотруднику нужно постоянное право, выдайте встроенную роль отдельным решением администратора.

## Как откат проверен

- Автоматически: `apps/api/src/integration/custom-roles-acceptance.database.spec.ts` на настоящем Postgres. Тест выключает и включает переключатель тем же HTTP-вызовом, что и экран, и проверяет, что роли и назначения сохранились, встроенные роли не изменились, а после включения роль работает снова без пересоздания.
- Построчно по маршрутам: `apps/api/src/modules/auth/custom-roles.acceptance.spec.ts` прогоняет каждый защищённый маршрут семи областей через настоящий `RolesGuard` (право есть, права нет, выключатель выключен, роль в архиве, право нельзя делегировать).
- Руками на копии базы перед первым включением в реальной организации: восстановить копию по `BACKUP_RESTORE_DISASTER_RECOVERY.md`, выполнить шаги «Включение» и «Откат» выше. Результат записать в запись выпуска (`RELEASE_GATE.md`).
