# Индивидуальные наборы прав: план общей модели ролей

**Статус:** DRAFT, проект реализации; новая модель в PR 349 не внедряется.
**Основание:** решение владельца DEC-CHKS-004 от 2026-10-27: «Нужны индивидуальные наборы прав; выполнить сверку и подготовить отдельный план модели ролей».
**Связи:** [реестр решений](../../status/OPEN_DECISIONS.md), [сверка чек-листов](../../evidence/2026-10-27-checklist-access-pr349.md), [контракт доступа](../../contracts/API_RBAC_MATRIX.md).

## Границы

Первая продуктовая потребность — индивидуальные права на чек-листы. Механизм авторизации должен быть общим для приложения: нельзя добавлять в `UserRole` очередную техническую роль «наблюдатель» или выдавать `instructor` как замену одному разрешению. Эта роль одновременно открывает другие возможности, включая работу с курсами.

Существующие пять системных ролей и `Membership` остаются совместимыми. Назначенный наблюдатель — отношение к конкретной сессии; настраиваемая роль — набор разрешений. Пользователь может обладать обоими независимо. Расширение списка допустимых наблюдателей и проведение своих сессий любой ролью относятся к PR 351/352; право выбирать человека в списке не означает право читать или менять чужие сессии.

Объём первой реализации и точные разрешения утверждаются по отдельному PR. Исходные отметки матрицы прототипа для PR 349 пока отсутствуют: неподтверждённые права не становятся требованиями этого плана.

## Модель разрешений и данных

- В коде определить стабильный каталог действий с допустимыми областями: собственный объект, назначенный наблюдатель, команда, организация. Политики `rolePolicies` служат исходной совместимой конфигурацией системных ролей. Названия действий, допустимость делегирования и области должны быть явными; нельзя трактовать произвольную строку роли как разрешение.
- Предложить аддитивные сущности `CustomRole` (организация, имя, состояние, версия), `CustomRolePermission` (роль, ключ действия, область) и `UserCustomRoleAssignment` (организация, пользователь, роль, назначивший, состояние). Уточнить имена по схеме перед реализацией. Составные ограничения должны исключать связи ролей и пользователей разных организаций, а уникальные ключи — повторные назначения и разрешения.
- Системные роли не копировать в изменяемые записи каждой организации. Существующие `Membership.role` и `UserRole` не заменять именами пользовательских ролей. Миграция не создаёт дополнительных прав для текущих пользователей.
- В первом варианте использовать объединение разрешённых действий и областей, без отдельного механизма явных запретов. Если нужен `deny`, его приоритет требует отдельного решения до реализации.
- Редактирование и назначение пользовательских ролей разрешить действующим администраторам собственной организации. Само управление ролями, выдача системного `admin` и доступ к другой организации не входят в делегируемый каталог первого этапа.

## Проверка доступа

Сначала определяется текущий пользователь и организация, затем действующие системные членства и пользовательские разрешения из БД. Сейчас `RolesGuard` уже читает `Membership` на каждом запросе и кеширует результат только внутри запроса. Новая модель должна сохранить эту актуальность: отзыв назначения или изменение набора прав действует со следующего запроса. Разрешения не записываются в JWT как долгоживущая копия.

Разрешение на действие и область объектов проверяются отдельно. Общий resolver возвращает области, которые сервис переводит в фильтры Prisma с обязательным `organizationId`. Выдача разрешения на всю организацию не подменяет `user.roles` значением `admin`.

Для каждого действия нужна собственная область. Объединение «команда или назначенные мне сессии» допустимо для чтения, но не для проведения чужой сессии. Проверка доступа выполняется также при идемпотентном повторе; кеш не выдаёт ответ по чужому объекту или старому набору прав.

Получатели уведомлений определяются событиями и участием в объекте на сервере. Право читать уведомления относится только к своим записям; пользовательская роль не может подставлять получателей или открывать чужой inbox.

## Контрольные сценарии первой вертикали

Пользователь с системной ролью learner и отдельным правом авторства листов может создавать листы, но не курсы. Назначенный наблюдатель с разрешением проведения работает только со своими сессиями и не получает командную аналитику. Каталог должен явно задавать необходимые зависимости действий (например, авторство и чтение библиотеки); состав набора проверяется при сохранении, без скрытой выдачи административных прав.

## Этапы реализации

| Этап | Результат | Проверка готовности |
| --- | --- | --- |
| CROLE-01 — каталог и совместимость | Каталог действий/областей и адаптер системных `rolePolicies`; утверждён список делегируемых действий чек-листов | Старые разрешения и запреты всех пяти ролей воспроизводятся; отдельно проверены совмещённые роли и различие чтения/действия |
| CROLE-02 — хранение | Аддитивные таблицы ролей, разрешений и назначений; версии, архивирование, tenant-ограничения | PostgreSQL: уникальность, конкурентное редактирование, запрет чужих связей; старые членства работают без backfill |
| CROLE-03 — guard и области | Resolver эффективных прав и действие-специфичные фильтры; переключение по организации выключено по умолчанию | Отзыв со следующего запроса; IDOR, подмена роли/организации, повтор кешированного запроса, multi-role; существующие проверки доступа сохранены |
| CROLE-04 — вертикаль чек-листов | Применение каталога к согласованным действиям листов, сессий и отчётов | Матрица allow/deny по каждому действию и области на реальном PostgreSQL; получение результатов не обходит `feedbackVisibility` и ограничения геоданных |
| CROLE-05 — управление | Версионируемый CRUD ролей и назначений, аудит, API собственных эффективных возможностей; затем экран настройки | Администратор не назначает чужую роль, не делегирует управление ролями; RU/EN/KK/ZH, keyboard/axe, контролируемые visual baselines |
| CROLE-06 — расширение | Отдельная миграция владельцев остальных модулей на общий механизм | По одному модулю с сохранением его object scope; endpoint без явной политики остаётся запрещённым |

Для CROLE-03 сначала сравнить старое и новое решение на системных ролях в тестах и диагностическом режиме. Не включать новую выдачу прав, пока различия не разобраны. Нельзя включить пользовательское разрешение на endpoint, пока его сервис продолжает выводить область исключительно из `user.roles`.

Для CROLE-05 контракт изменения включает версию и ответ 409 при устаревшей записи. Аудит хранит автора, организацию, целевую роль/пользователя и изменения разрешений. Архивирование прекращает действие назначений, сохраняя историю. Интерфейс получает эффективные возможности через API для отображения, но решение принимает сервер. Кнопка создания роли появляется после готовности backend-контракта.

## Выпуск, откат и документация

Включать по организации после прохождения матрицы. Откат переключателя возвращает системные политики, оставляя новые таблицы и историю; пользовательская роль не преобразуется в системную. Проверить откат на копии тестовой БД и описать миграционные процедуры в соответствующем runbook.

`docs/generated/RBAC.md` продолжает описывать статический каталог и системные роли. Текущие пользовательские роли отдельных организаций — данные БД, а не коммитящийся Markdown-инвентарь. Генератор, API/RBAC-контракты и документация миграции обновляются вместе с реализацией, из реальных owner-source.

Приёмка будущей модели требует unit, PostgreSQL/HTTP allow-deny и IDOR-тестов, отзыва прав без нового входа, проверки чтения/записи разными областями и совместимости существующих пользователей. Снимки назначенных листов, результаты, аудит и правила `canComplete` не мигрируют автоматически из-за изменения прав.
