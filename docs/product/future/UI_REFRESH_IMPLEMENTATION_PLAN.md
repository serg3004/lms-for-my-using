# План реализации: визуальный рефреш «Оргструктура» и «Чек-лист-сессии»

**Основание:** прототипы `ORG_STRUCTURE_UI_REFRESH_PROTOTYPE.html` и
`CHECKLIST_SESSIONS_UI_REFRESH_PROTOTYPE.html` (лежат в этой же папке). Они не зарегистрированы в
CI-enforced `docs/lms-ui-prototypes-complete/manifest.json`. Это установленная практика для прототипов,
которые обслуживают один конкретный product-план (так же был оформлен прототип
`CHECKLIST_WORKPLACE_TRAINING_IMPLEMENTATION_PLAN.md`).

**Статус:** не начато. Ни один PR из этого плана ещё не открыт.

**Решения владельца продукта (2026-09-26):**
- shell (сайдбар и топбар) приводится к прототипу во всём приложении, а не только в оргструктуре;
- мобильные таблицы чинятся на всех экранах, а не только в оргструктуре;
- счётчики на вкладках оргструктуры отдаёт один новый лёгкий серверный запрос.

## 0. Границы — обязательно к соблюдению

- Рефреш только визуальный. Дерево подразделений, должности, требования, группы, CSV-импорт с историей и
  цикл чек-лист-сессий уже реализованы и не переписываются. Весь существующий функционал (поиск, фильтры,
  действия, карточка подразделения, архивирование) сохраняется, даже если в прототипе его нет.
- Палитра не меняется. Основной цвет и фон — из org-theme (`apps/web/src/shared/theme.ts`,
  `defaultThemeSettings`), статусные цвета — из `apps/web/src/styles/tokens.css`, шрифт — Manrope
  (`apps/web/src/styles/global.css`). Ни один PR не меняет `tokens.css` и `defaultThemeSettings`.
- Тёмная тема на HTML-страницах прототипов — только оформление просмотрщика. В приложении тёмной темы нет,
  этот план её не вводит.
- Новый бэкенд — только эндпоинт счётчиков (PR 309). Остальные PR — только `apps/web`.
- Каждый PR меняет shared UI или layout, поэтому по `AGENTS.md` обязательны `pnpm test:visual` и
  `pnpm test:a11y`. Baselines обновляются только через `.github/workflows/update-visual-baselines.yml` из
  ветки с актуальным `main`, изменённые PNG просматриваются до merge.

## 0.1. Известный функциональный пробел вне scope

`ChecklistBuilder` сохраняет определения `contextFields` листа, но `ChecklistSessionConduct.tsx` их не
рендерит и не собирает. Это функциональный пробел чек-лист-модуля (уже отмечен в
`CHECKLIST_WORKPLACE_TRAINING_IMPLEMENTATION_PLAN.md`), а не визуальное расхождение. Этот план его не
закрывает.

## 0.2. Текущее состояние оргструктуры (проверено 2026-09-26 на `main` `654908d`)

Все 5 вкладок отрендерены локально под администратором и сравнены с прототипом.

- Вкладки — `OrgStructureTabs` в `apps/web/src/shared/adminPage.tsx`, обычные `<a href>` на 5 роутов.
  Каждый клик перезагружает страницу. Визуально это совпадает с прототипом, переделка на client-side
  панели не требуется.
- У каждой вкладки свой заголовок и разный eyebrow («Подразделения», «Оргструктура», «Группы»,
  «Organization structure»). В прототипе один общий заголовок раздела и счётчики на вкладках.
- «Импорт и история» (`AdminOrgStructureToolsPage.tsx`) полностью на английском при RU-локали: строки
  захардкожены, `brandLabel="LearnSpace"` и свои `navItems` вместо `t(...)`. В колонке автора — полный UUID.
- Mobile 390: таблицы `DataTable` без `data-priority` на колонках (должности, требования, группы, курсы)
  сжимают колонки до ~35px, текст переносится по одной букве. На `/admin/users` приоритеты заданы, там
  таблица читается.
- Карточка выбранного подразделения на 1440px: ряд действий выходит за край карточки на 52px. На mobile
  кнопка «+ Добавить корневое подразделение» обрезана краем экрана.

## PR 309 — API: счётчики разделов оргструктуры

**Цель:** один лёгкий запрос отдаёт числа для всех пяти вкладок, без загрузки чужих списков.

**Зависимости:** нет.

**Что необходимо сделать:**
- `GET /api/v1/org-structure/counts` в существующем модуле `org-structure-admin`
  (`org-structure-admin.controller.ts` / `.service.ts`), без нового модуля.
- Ответ — пять чисел: `departments`, `positions`, `positionCourses`, `groups`, `historyEvents`.
  Считаются только активные записи организации текущего пользователя (без архивных и удалённых), история —
  все записи `OrgStructureEvent` организации.
- Только `count()`-запросы Prisma, без выборки строк.
- Доступ — `rolePolicies.departmentsRead`, как у `GET /org-structure/history`.
- Клиент: `getOrgStructureCounts()` в `apps/web/src/shared/api/org-structure-admin.ts`.
- Перегенерировать `docs/generated` через `pnpm docs:generate`, проверить `docs/contracts/API_CONTRACTS.md`
  и `docs/contracts/API_RBAC_MATRIX.md`.

**Критерии готовности:**
- [ ] unit-тест сервиса: архивные записи не учитываются, чужая организация не учитывается;
- [ ] тест контроллера: роль без `departmentsRead` получает 403;
- [ ] `pnpm docs:generate:check` и `pnpm docs:consistency:test` зелёные.
