# План: регистрация и учётные записи пользователей (приглашение по письму, настраиваемые поля пользователя, политика и смена пароля, временный пароль, подразделение и роль при создании, список «ожидают входа», импорт из файла, защита входа, журнал входов и устройства, архив, профиль, массовые действия) (этап 13)

**Основание:** запрос владельца 2026-11-18: проверить, как проходит регистрация пользователей, и составить план по найденным пробелам. Нумерация продолжает [`CUSTOM_ROLES_IMPLEMENTATION_PLAN.md`](./CUSTOM_ROLES_IMPLEMENTATION_PLAN.md) (последний номер PR 486).
**Статус:** план согласован владельцем 2026-11-18 (все вопросы закрыты); код не начат. Каждый PR стартует только по слову «Выполняй PR N».
**Цель:** пользователя заводят безопасно и быстро: администратор или руководитель вводит email и данные (или загружает файл), человек получает письмо на своём языке и сам задаёт пароль; пароли отвечают политике; вход защищён от подбора; видно, кто и где входил; сотрудника можно архивировать и восстановить без потери истории.

## 0. Границы

- **Как есть сейчас (проверено по коду 2026-11-18):** самостоятельной регистрации нет; пользователя создаёт администратор или руководитель (`usersCreate`: admin, manager; руководитель в пределах команды) через `POST /users`, пакетно `POST /users/bulk` (до 50) и `POST /users/import` (до 100 строк, режим `validateOnly` с отчётом по строкам; в интерфейсе нет); пароль придумывает администратор (`createUserSchema`: от 8 знаков), роль выдаётся вторым запросом `POST /memberships` (только администратор), подразделение назначается отдельно; статус `invited` есть в схеме, но не используется; «Забыли пароль» работает через `PasswordResetToken`, письма идут через `common/mail` (Gmail SMTP); смены своего пароля внутри системы нет; блокировки учётной записи после серии неудач нет (есть только общий ограничитель `api-hardening`); архивирования нет (статус `archived` и `deletedAt` в схеме, но API умеет только `active` и `suspended`); журнала входов нет (есть `Session` и `lastLoginAt`).
- **Не входит в этот план:** двухфакторный вход и единый вход через корпоративный аккаунт (Google, Microsoft); самостоятельная регистрация и заявки на доступ (система корпоративная, пользователей заводит организация). Если понадобятся, это отдельный план.
- Секреты и пароли в репозиторий, логи и документы не попадают; токены хранятся только в виде хешей (как `PasswordResetToken.tokenHash`); ответы «пользователь есть или нет» не раскрывают существование аккаунта.
- Все письма и экраны на RU, EN, KK, ZH; язык письма приглашения берётся из `locale`, выбранного при создании пользователя; слово «эталон» вместо названия стороннего продукта; бюджет CSS расходуется минимально.
- Права: приглашения и импорт доступны администратору и руководителю (в пределах команды), потом делегируются по плану ролей (PR 483); архивирование, разблокировка и журнал входов администратору; все действия пишутся в аудит.

## PR 489 — Временный пароль и обязательная смена при первом входе

**Статус:** ✅ выполнено (PR 489, личный временный пароль); общий пароль на партию перенесён в PR 501 по решению владельца 2026-11-21
**Основание:** разрыв 65.
**Цель:** запасной путь для людей без почты: администратор выдаёт временный пароль, человек обязан сменить его при первом входе.
**Зависимости:** PR 488.

**Что необходимо сделать:**
- флаг `mustChangePassword` у пользователя (аддитивная миграция); при выдаче временного пароля администратором флаг ставится, пароль генерируется сервером по политике и показывается один раз, в журнал и аудит не пишется;
- два вида выдачи, выбирает администратор (решение владельца 2026-11-18): (а) личный временный пароль у каждого, одноразовый, срок 7 дней, по умолчанию; (б) общий стандартный пароль на партию пользователей. Для (б) обязательны ограничения: действует только до первого входа конкретной записи и не дольше срока партии (по умолчанию 72 часа), только вместе с подтверждением личности (организация, табельный номер, фамилия), строгое ограничение попыток, запись каждого входа с этим паролем в аудит, письмо или сообщение настоящему владельцу записи о входе; если за срок партии (72 часа) пользователь так и не вошёл, администратору приходит сводка «не вошли» со списком (решение владельца 2026-11-18), пароль партии при этом перестаёт действовать; интерфейс предупреждает, что общий пароль слабее личного;
- вход с флагом ведёт только на экран смены пароля; остальной API до смены закрыт (кроме выхода и смены пароля); после смены флаг снимается;
- вариант «создать с временным паролем» в окне создания пользователя; «Сбросить пароль» из карточки (с подтверждением) для действующего пользователя;
- права: администратор и руководитель в пределах команды; аудит;
- тексты RU/EN/KK/ZH, тесты: модульные, интеграционные (закрытый API до смены, повторный вход), e2e.

**Критерии готовности:**
- [x] с временным паролем нельзя ничего, кроме смены пароля;
- [x] временный пароль показывается один раз и нигде не сохраняется открытым текстом;
- [x] тесты, контракты, CI зелёный.

**Что вошло в PR 489:** личный временный пароль (12 знаков, буквы и цифры без похожих знаков, по политике организации), одноразовый и на 7 дней; `POST /users/:id/temporary-password` и `POST /users` с `temporaryPassword: true` (права и область как у «Сбросить пароль»: администратор и руководитель в пределах команды, делегированный регистратор в своём подразделении); выдача завершает все сеансы пользователя и прежние ссылки сброса; вход с таким паролем возможен один раз, затем API отвечает `403 PASSWORD_CHANGE_REQUIRED`, кроме `/auth/*` (выход, свои данные, смена пароля); в вебе вместо любой страницы показывается экран «Задайте свой пароль»; пароль показывается один раз и не попадает ни в аудит, ни в журналы. Общий пароль на партию (вариант «б») сделан не был: он требует подтверждения личности по табельному номеру (PR 499–501), поэтому перенесён в PR 501 вместе со сводкой «не вошли». Отдельного e2e-сценария нет, путь покрыт интеграционным тестом на Postgres (`temporary-password.database.spec.ts`).

**Цель:** на общем компьютере, киоске или планшете цеха пользователь входит без ввода пароля: на экране показан QR, он подтверждает вход на своём телефоне, где уже вошёл.
**Зависимости:** PR 488, PR 493, PR 494 (журнал входов и устройства).

**Заметки по подготовке:**
- Работает как вход в мессенджер на компьютере: устройство запрашивает «ожидающий вход» с одноразовым кодом, показывает его как QR; телефон, где пользователь уже вошёл, сканирует, видит название устройства и место и подтверждает; устройство получает сессию.
- Главный риск: обман «покажи QR», когда злоумышленник просит подтвердить его вход. Меры: на телефоне показываются устройство, браузер, примерное место и время; код живёт 2 минуты и подтверждается один раз; подтверждение требует разблокировки телефона (сессия приложения) и явной кнопки; вход записывается в журнал входов; пользователь может завершить такую сессию.
- Сессия, полученная по QR, короткая (например 8 часов, настраивается) и не даёт ролей с широкими правами, пока пользователь не введёт пароль; ограничение по ролям настраивает администратор (вопрос 17).

**Что необходимо сделать:**
- `POST /auth/qr/start` (публичный, ограничение частоты по IP): создаёт ожидающий вход с хешем кода, сроком и описанием устройства; `GET /auth/qr/status` (опрос или SSE): ждёт подтверждения; `POST /auth/qr/approve` (вошедший пользователь): подтверждает; `POST /auth/qr/deny`;
- экран входа: вкладка «Войти по QR» (QR крупно, таймер, обновление), экран подтверждения на телефоне (устройство, место, время, «Подтвердить» и «Это не я»);
- политика: включается администратором по организации и по ролям, срок сессии, запрет для ролей с правами администратора по умолчанию;
- безопасность: одноразовость, срок, привязка подтверждения к конкретному запросу устройства, защита от гонки и повтора, одинаковые ответы, аудит и журнал входов (PR 494), уведомление «выполнен вход по QR»;
- тесты: модульные (срок, одноразовость), интеграционные (подтверждение, отказ, повтор, чужой пользователь), безопасность (нельзя подтвердить вход без собственной сессии, нельзя использовать код дважды), e2e (два контекста браузера), визуальные эталоны.

**Критерии готовности:**
- [ ] вход на устройстве по QR после подтверждения на телефоне работает, код одноразовый и живёт 2 минуты;
- [ ] на телефоне видно устройство и место, вход попадает в журнал и его можно завершить;
- [ ] политика по организации и ролям соблюдается;
- [ ] тесты, CI зелёный;
- [ ] проверка владельцем на реальном телефоне и компьютере.

## PR 506 — QR-бейдж сотрудника: вход только для прохождения

**Статус:** план
**Основание:** разрыв 83; запрос владельца 2026-11-18 (по QR можно только пройти чек-лист, тест или курс).
**Цель:** у сотрудника есть личный QR на бейдже; поднеся его к камере общего устройства, он попадает только в прохождение назначенных ему чек-листов, тестов и курсов.
**Зависимости:** PR 504 (личный QR и токены), PR 505 (одноразовые ограниченные сессии), PR 493, PR 494.

**Заметки по подготовке:**
- QR на бейдже это долгоживущий токен сотрудника (не одноразовый, в отличие от активации). Его легко потерять или сфотографировать, поэтому он сам по себе открывает только **ограниченный режим**: список назначенного сотруднику и прохождение; без отчётов, профиля, настроек и прав руководителя.
- **Что такое PIN:** короткий цифровой пароль из 4–6 цифр, который знает только сам сотрудник, как PIN банковской карты. После скана бейджа система просит ввести PIN. Бейдж это «что у вас есть», PIN это «что вы знаете»; вместе они надёжнее. Включается в настройках организации (по умолчанию включён, вопрос 18).
- Результаты теста и чек-листа пишутся на имя сотрудника, поэтому чужой человек с чужим бейджем исказил бы чужие результаты. Поэтому рекомендуется второй признак: короткий PIN сотрудника (4–6 цифр, вопрос 18).
- Токен хранится в базе только в виде хеша; QR печатается на бейдже, отзыв и перевыпуск при потере.

**Что необходимо сделать:**
- аддитивная миграция: личный токен бейджа (`UserBadge`: пользователь, хеш токена, PIN-хеш, состояние, выдан, отозван, срок необязателен, последний вход);
- ограниченная сессия «киоск»: права только на чтение своих назначений и на прохождение (чек-лист самостоятельно, тест, курс); остальное API закрыто на уровне гарда; короткий срок (например 30 минут бездействия), после завершения прохождения сессия сворачивается;
- вход по бейджу: камера читает QR, затем PIN (если включён); ограничение попыток по токену и IP, блокировка после серии неудач (PR 493), одинаковый ответ при ошибке, запись в журнал входов (PR 494, помечено «бейдж»);
- сотрудник в приложении нажимает «Бейдж потерян» (решение владельца 2026-11-18): QR сразу отзывается системой, администратору приходит уведомление, он создаёт и печатает новый бейдж;
- администратор: выпуск, печать (лист бейджей пачкой, как в PR 504), отзыв и перевыпуск при потере, сброс PIN; сотрудник видит в профиле «Мой бейдж» и может сообщить о потере;
- запрещено для ролей с правами администратора и руководителя (бейдж не открывает управление);
- состояния и тексты RU/EN/KK/ZH, большие кнопки для планшета и перчаток (цель нажатия 56 px), доступность;
- аудит выпуска, отзыва, входов; тесты: модульные (токен, PIN, срок), интеграционные (ограничение прав сессии: нельзя открыть отчёты и чужие данные, нельзя пройти чужое назначение), безопасность (перебор, повтор, отозванный бейдж), e2e (скан эмулируется, PIN, пройти тест), визуальные эталоны.

**Критерии готовности:**
- [ ] по бейджу (и PIN) сотрудник проходит только назначенное ему, остальное закрыто;
- [ ] отозванный и потерянный бейдж не работает, перевыпуск создаёт новый QR;
- [ ] вход по бейджу в журнале входов, перебор ограничен;
- [ ] тесты, визуальные эталоны, CI зелёный;
- [ ] проверка владельцем на реальном планшете в цеху.

## PR 507 — Карточка сотрудника по сканированию QR

**Статус:** план
**Основание:** разрыв 84; запрос владельца 2026-11-18 (навёл камеру и увидел всё о сотруднике).
**Цель:** любой зарегистрированный в системе пользователь организации (и внешний проверяющий) сканирует QR сотрудника и видит сводку: какие курсы пройдены и какие нет, удостоверения и просроченные, чек-листы.
**Зависимости:** PR 506 (QR бейджа), PR 473–474 (отчёт по пользователю), удостоверения (`Certificate`), PR 499 (поля сотрудника).

**Заметки по подготовке:**
- Данные уже есть по частям: назначения и прогресс курсов, результаты тестов, `Certificate` со сроками, прохождение чек-листов; отчёт по пользователю в плане PR 473–474.
- **Решение владельца 2026-11-18:** карточку может открыть **каждый зарегистрированный в системе пользователь** своей организации, не только руководители. QR содержит только непрозрачный токен, не данные; чтобы увидеть карточку, сканирующий должен войти в систему.
- Поскольку карточка видна всем, администратор в настройках организации выбирает, **какие блоки видны всем** (по умолчанию: ФИО, фото, должность, подразделение; курсы: пройден или нет; удостоверения: действует, истекает, просрочено; чек-листы: назначен, пройден, просрочен), а подробности (баллы, попытки, замечания и результаты по пунктам, персональные поля) только по правам (администратор все, руководитель своя команда, инструктор свои курсы, сам сотрудник свой профиль). Каждый просмотр пишется в аудит, сотрудник видит, кто смотрел его карточку (вопрос 20).
- **Без входа:** сканирование ничего не раскрывает: экран с шуточным предупреждением (смайлик и «ай-ай-ай, сначала войдите») и предложением войти; такое сканирование пишется в журнал (время, IP, устройство, чей бейдж) и при серии подряд уведомляет администратора.
- **Внешний проверяющий** (например, инспектор): администратор заносит его в систему как отдельный тип пользователя, указывает, какие именно поля и блоки он видит (по умолчанию ФИО, фото, «допуск действителен: да или нет»), срок действия доступа; вход по приглашению (PR 487), больше ничего в системе ему не доступно.

**Что необходимо сделать:**
- маршрут и страница «Карточка сотрудника» по токену бейджа: шапка (ФИО, фото, должность, подразделение, табельный номер, графики и поля по правам), блоки: курсы (пройдены, в процессе, не начаты, просрочены, баллы), удостоверения (действуют, истекают, просрочены, сроки), чек-листы (пройденные, назначенные, просроченные, результаты), сводный признак допуска (все обязательные удостоверения и курсы действуют);
- настройка «что видно всем» и «что видно по правам» (по организации), поля, скрытые от роли, не показываются; сотрудник другой организации не открывается и не раскрывается;
- без входа: экран «ай-ай-ай» с входом и возвратом к карточке; запись в журнал и уведомление администратору при серии; ограничение частоты по IP;
- внешний проверяющий: отдельный тип пользователя с настраиваемым набором видимых полей и сроком доступа, вход по приглашению, остальное API закрыто на уровне гарда;
- телефон в первую очередь (камера и большие блоки), разворачиваемые разделы, состояние «данных нет», быстрая отметка «проверено» с записью в аудит (кто и когда смотрел сотрудника), печать и выгрузка карточки по желанию;
- аудит каждого просмотра (кто смотрел кого, когда), потому что это персональные данные; сотрудник может видеть, кто смотрел его карточку (вопрос 20);
- тексты RU/EN/KK/ZH, доступность, бюджет CSS, e2e и визуальные эталоны на 390 и 1280 px;
- тесты: модульные (расчёт допуска), интеграционные на Postgres (область, чужая организация, скрытые поля, отозванный бейдж), безопасность (нельзя получить данные без входа и права, нельзя перебирать токены).

**Критерии готовности:**
- [ ] после скана и входа проверяющий видит курсы, удостоверения, чек-листы и признак допуска, цифры совпадают с отчётом по пользователю;
- [ ] любой вошедший пользователь организации видит только те блоки, которые разрешил администратор, подробности только по правам; без входа ничего не раскрывается и пишется в журнал;
- [ ] внешний проверяющий видит только заданные поля, просмотры пишутся в аудит;
- [ ] отозванный бейдж не открывает карточку;
- [ ] тесты, визуальные эталоны, бюджет CSS, CI зелёный;
- [ ] проверка владельцем на телефоне с реальным бейджем.
