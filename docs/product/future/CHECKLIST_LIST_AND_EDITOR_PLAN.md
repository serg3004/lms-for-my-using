# План: список листов, папки, настройки модуля на каждый лист и правки редактора чек-листов (этап 6)

**Основание:** замечания владельца 2026-10-31 по экрану «Админ → Чек-листы» (скриншоты: список в LearnSpace и список «Листы наблюдения» в эталоне).
**Статус:** план согласован владельцем 2026-10-31 («Принимаю всё»), код не начат; реализация только по команде «делай» с номером PR. Нумерация PR 393–406 (381–392 заняты планом лонгрида).
**Цель:** привести список листов к эталону: у каждой строки доступно «Удалить», есть групповой выбор с массовыми действиями, видно кто создал лист и когда (дата и время), листы раскладываются по вложенным папкам (до 5 уровней); пороги, цвета, геолокацию, видимость обратной связи и наблюдателей можно задать отдельно для каждого листа.

## 0. Границы

- Новых пунктов меню нет, только экран «Чек-листы», вкладка «Чек-листы».
- Права не расширяются: массовое действие применяется к листу, только если то же действие разрешено над одним листом (создатель/админ при `allowEditByAll = false`, роль, организация). Остальные пропускаются с причиной.
- Правило удаления листа не меняется: лист с активным назначением удалить нельзя (мягкое удаление `deletedAt`, завершённые результаты сохраняются). При массовом удалении (и при удалении папки) такие листы не удаляются, а **пропускаются и переводятся в черновик** (решение владельца 2026-10-31); в отчёте операции они помечены «переведён в черновик: есть активные назначения».
- Миграция одна, в PR 395 (аддитивная); для PR 393–394 миграций нет: `createdBy`, `createdAt` уже есть в `checklists`. Тексты через i18n RU/EN/KK/ZH. Бюджет CSS (90 KiB) почти исчерпан, новые стили минимальны.
- «Перемещение» — смена статуса (архив, черновик, публикация), копирование и перемещение листов в папки (решение владельца 2026-10-31). Папки: создание, переименование, удаление, вложенность до 5 уровней (корневая = уровень 1, подтверждено), общие на всю организацию (пока).

## PR 395 — Папки листов: модель и API

**Статус:** не начат.
**Основание:** разрыв 5 (решение владельца 2026-10-31).
**Цель:** иерархия папок организации и привязка листа к папке на сервере.
**Зависимости:** PR 394.

**Что необходимо сделать:**
- миграция (аддитивная): таблица `checklist_folders` (`id`, `organization_id`, `parent_id` → саму себя, `name`, `visible_to_staff` (по умолчанию выключено), `created_by`, `created_at`, `updated_at`, `deleted_at`), в `checklists` поле `folder_id` (пусто = корень «Все листы»); индекс по `(organization_id, parent_id)`;
- правила: глубина не больше 5 уровней (корневая папка = уровень 1); имя 1–255 символов, уникально среди соседей без учёта регистра; папку нельзя перенести в себя или в своего потомка; папки общие на организацию;
- API: `GET /checklist-folders` (всё дерево с числом листов), `POST /checklist-folders`, `PATCH /checklist-folders/:id` (переименование и перенос), `DELETE /checklist-folders/:id`; `PATCH /checklists/:id` и массовое `POST /checklists/bulk` получают действие `move { folderId | null }`;
- удаление папки удаляет **всё внутри**: подпапки на всех уровнях и листы (мягкое удаление `deletedAt`, завершённые результаты сохраняются). Лист с активным назначением не удаляется, а переводится в черновик и переносится в корень «Все листы»; в ответе перечислены удалённые папки, удалённые листы и такие переведённые листы; подтверждение в интерфейсе показывает эти числа заранее; в аудит пишется одна запись операции;
- доступ к папке: видят и меняют папку администратор и её создатель; флажок «Видна всем ролям, кроме обучающегося» (`visible_to_staff`) открывает её на просмотр остальным ролям (наблюдатель, инструктор, руководитель и т. д.); обучающийся папки и их дерево не видит никогда; подпапка видна, только если видна вся цепочка родителей; листы скрытой папки не показываются в списке тем, кто папку не видит (назначения, сессии и отчёты не меняются); менять флажок и перемещать папки могут только администратор и создатель папки;
- копирование листа остаётся в той же папке; сессии, назначения и результаты папками не затрагиваются;
- права: управляют папками те же роли, что листами; перенос листа требует права редактировать этот лист (PR 362в);
- документация: `API_CONTRACTS.md`, схема данных.

**Критерии готовности:**
- [ ] создание, переименование, перенос и удаление папок, ограничение 5 уровней, защита от циклов и дублей имён;
- [ ] удаление папки удаляет все вложенные папки и листы; лист с активным назначением переведён в черновик и перенесён в корень;
- [ ] доступ: администратор и создатель всегда, остальные роли (кроме обучающегося) по флажку, обучающийся никогда; цепочка родителей учитывается;
- [ ] тесты на реальной Postgres: изоляция организаций, глубина, циклы, мягкое удаление;
- [ ] CI зелёный.

## PR 397 — Настройки модуля на каждый лист: «Как в организации»

**Статус:** не начат.
**Основание:** вопрос владельца 2026-10-31 («нет возможности настраивать каждый чек-лист отдельно»); разрыв 6. Решение владельца: переопределяются все пять групп настроек.
**Цель:** у каждого листа можно переопределить пять настроек модуля; по умолчанию лист берёт настройку организации.
**Зависимости:** PR 368, PR 369б, PR 365; не зависит от PR 393–396 (можно делать параллельно).

**Что переопределяется на листе (остальное остаётся на организации):**
1. пороги высокого и низкого результата (`highPerformanceThreshold`, `lowThreshold`);
2. цвета результата (`resultColorLow/Mid/High`);
3. геолокация по умолчанию (у листа уже есть `defaultLocationCapturePolicy`; значение «пусто» теперь означает «как в организации», явное значение, включая «выключено», перекрывает организацию);
4. видимость обратной связи сотруднику (`feedbackVisibility`);
5. кто может быть наблюдателем (`observerEligibility`, роли, список людей).

Включение и выключение модуля целиком остаётся на организации.

**Что необходимо сделать:**
- миграция (аддитивная): в `checklists` необязательные поля `high_threshold_override`, `low_threshold_override`, `result_color_low/mid/high_override`, `feedback_visibility_override`, `observer_eligibility_override`, `observer_roles_override`, `observer_user_ids_override`; пусто = как в организации; у существующих листов все пустые, поведение не меняется;

## PR 400 — «Картинка листа» не отображается после загрузки

**Статус:** не начат. Замечание владельца 2026-10-31 (скриншот: после загрузки картинки в блоке «Картинка листа» остаётся значок), внесено в план, код не пишется до «делай».
**Основание:** разрыв 9, PR 355.
**Цель:** загруженная картинка видна в редакторе, в списке листов и у сотрудника; при ошибке пользователь видит причину, а не молчаливую заглушку.
**Зависимости:** PR 355.

**Подтверждение (скриншот владельца 2026-10-31, «Мои чек-листы», фото к критерию «СИЗ есть»):** прикреплённое фото показывается сломанной миниатюрой с именем файла вместо картинки, то есть те же подписанные ссылки не открываются и у сотрудника; исправление должно покрывать и фото критериев в прохождении (PR 406), а не только обложку.

**Причина (найдена по коду и конфигурации рабочего окружения 2026-10-31):**
1. Сайт отдаёт nginx (сервис `web`, `infra/nginx/security-headers.conf`) с политикой безопасности `img-src 'self' data: blob:`. Картинка листа рисуется как `<img src="подписанная ссылка">`, а ссылка ведёт на хранилище (сервис `minio`, домен `minio-production-aece.up.railway.app`), то есть на чужой для страницы адрес. Браузер блокирует такую картинку по политике, при этом загрузка и запись в базу проходят нормально. Компонент `ChecklistCover` при ошибке изображения молча показывает заглушку, поэтому владелец видит только значок. Вывод следует из кода и из конфигурации сервисов; сам запрос в браузере владельца я не воспроизводил.
2. Усугубляет: у сервиса `api` в Railway нет переменной `S3_FILE_ORIGIN`, значит подписанные ссылки собираются на адрес `S3_ENDPOINT`. Если там внутренний адрес (`*.railway.internal`), браузер до него не дойдёт вовсе. Значение переменной прочитать не удалось: чтение переменных рабочего окружения заблокировано правилами доступа; `[НЕ ПРОВЕРЕНО]`.
3. Те же подписанные ссылки используются для фото в проверке и отчёте (`ChecklistReviewPhotoEvidence`), значит и они, скорее всего, не открываются в браузере; `[НЕ ПРОВЕРЕНО]`. PDF не затронут (сервер читает файлы напрямую).

**Решение (рекомендуемое):** не открывать хранилище браузеру и не ослаблять политику безопасности. Файл отдаёт сам API: новый `GET /checklists/:id/cover/file` (та же проверка прав, что у `GET /checklists/:id/cover`) читает объект из хранилища (сервер до хранилища достаёт, раз загрузка работает) и отдаёт байты с `Content-Type`, `Cache-Control: private` и `ETag` по `coverUpdatedAt`. Клиент скачивает файл обычным запросом с авторизацией и показывает как `blob:` ссылку (`blob:` в политике уже разрешён). Работает при любом значении `S3_ENDPOINT`, без публичного домена хранилища и без правок политики. Альтернатива (не рекомендуется): добавить домен хранилища в `img-src` и задать `S3_FILE_ORIGIN` на публичный адрес `minio`; требует правки окружения Railway и открывает хранилище наружу.

**Что необходимо сделать:**
- сервер: `GET /checklists/:id/cover/file` (потоком, до 8 МБ, права как у обложки, 404 без обложки), тесты прав и содержимого на реальной Postgres и тестовом хранилище; такой же маршрут для фото ответов в проверке и отчёте, если подтвердится п. 3;
- клиент: `ChecklistCover` и `ChecklistReviewPhotoEvidence` получают файл запросом с авторизацией, освобождают `blob:` ссылку при смене и размонтировании, кеш по `coverUpdatedAt`; старый запрос подписанной ссылки для обложки не используется;
- интерфейс: при ошибке загрузки картинки в редакторе листа сообщение «Не удалось показать картинку» и кнопка «Повторить», в списках остаётся заглушка;
- документация: `docs/contracts/API_CONTRACTS.md`, `docs/contracts/STORAGE_UPLOAD_STATUS.md` (правило: браузер не обращается к хранилищу напрямую);
- политика безопасности остаётся без изменений (тест в проверке заголовков подтверждает, что `img-src` не расширен);
- после выкладки владелец проверяет обложку в редакторе, в списке листов и у сотрудника, фото в отчёте.

**Критерии готовности:**
- [ ] загруженная картинка видна в редакторе сразу после загрузки и после обновления страницы;
- [ ] картинка видна в списке листов и у сотрудника (плитки), фото в проверке и отчёте открываются;
- [ ] политика безопасности страницы не ослаблена, домен хранилища браузеру не нужен;

4. **Передача проверки другому сотруднику.** Если один лист заполняют несколько человек (смены, бригада), сотрудник может нажать «Передать проверку…», выбрать коллегу из доступных (подразделение, правила видимости, PR 345) и добавить заметку; незавершённая проверка со всеми внесёнными ответами и фото переходит к нему, прежний исполнитель видит статус «Передано» и больше не может править, новому приходит уведомление; история передач хранится в событиях проверки и видна в отчёте; нельзя передать завершённую проверку; права: исполнитель, его руководитель и администратор; запрет передачи самому себе и пользователям вне организации. 5. **Предпросмотр заполненного листа как в PDF.** Кнопка «Предпросмотр» (до и после завершения) открывает страницу в виде отчёта по образцу PR 371 (шапка, общая информация, группы, критерии с ответом, комментарием и фото, обратная связь, итог после завершения) с кнопками «Скачать PDF» и «Печать»; до завершения итог и баллы не показываются (п. 1), после завершения как в отчёте; серверный отчёт и PDF строятся сейчас для сессий, для самостоятельных прохождений нужна такая же сборка по экземпляру листа (`GET /checklist-instances/:id/report` и PDF) с теми же правами (сотрудник видит свой результат, остальные роли в своей зоне, PR 366).
6. Тексты RU/EN/KK/ZH, доступность (кнопки, окно просмотра фото, подтверждение), узкий экран и телефон (цель нажатия 44 px); документация: `API_CONTRACTS.md` (передача, отчёт по экземпляру), этот план.
7. Тесты: компонент (без баллов, отметка и окно фото, завершение, передача), серверные (права передачи, события, отчёт по экземпляру, изоляция организаций на реальной Postgres), e2e (пройти лист без баллов на кнопках, прикрепить и посмотреть фото, передать коллеге, завершить, открыть предпросмотр и PDF), визуальные эталоны.

**Критерии готовности:**
- [ ] на кнопках ответа при заполнении нет баллов, в отчёте и PDF они остаются;
- [ ] фото показывается отметкой «Фото вложено» и открывается кнопкой «Посмотреть фото», миниатюра больше не ломается;
- [ ] есть «Завершить проверку» (или «Отправить на проверку») с подтверждением и перечнем недостающего;

- [ ] «Предпросмотр» показывает заполненный лист в виде отчёта и даёт скачать PDF;
- [ ] права и изоляция организаций проверены на реальной Postgres;
- [ ] тесты, визуальные эталоны, CI зелёный; проверка владельцем на реальных листах.
