## PR 454 — Понятная ошибка сохранения листа с названием поля

**Статус:** не начат
**Основание:** замечание 32.
**Цель:** вместо «Validation failed» автор видит, какое поле и что не так («Поле «Опасности»: выберите набор ответов»), вкладка и блок подсвечены, фокус стоит на нужном поле.
**Зависимости:** нет.

**Заметки по подготовке (по коду):**
- `ChecklistBuilder.saveSettings` берёт из `ApiClientError.details` только первое поле и переводит на вкладку по `MAIN_TAB_FIELDS`; `settingsErrorMessage` показывает общее сообщение. Для полей общей информации и обратной связи (`contextFields.N.answerSetId` и др.), групп, критериев, шкал и изображений пути не сопоставлены с экраном.
- Нужно пройти все места сохранения в модуле листа и составить таблицу «путь поля → понятное название → вкладка/блок → элемент для фокуса»: настройки листа, поля общей информации, раздел и поля обратной связи, группы и критерии, шкалы уровней, изображения и подписи, миниатюра. Аудит записать в PR: где ещё выводится общее «Validation failed».
- Для «Выбор из набора ответов» без набора добавить проверку до отправки (клиентская), чтобы автор видел причину сразу; серверная проверка остаётся.

**Что необходимо сделать:**
- общая функция «ошибка проверки → список понятных строк с названием поля» и её использование во всех сохранениях листа; показ первой ошибки у кнопки, остальных списком, «!» на нужной вкладке и у блока;
- клик по ошибке и фокус ведут к полю (в том числе внутри блока обратной связи и общей информации);
- клиентская проверка поля обратной связи с типом «Выбор из набора ответов» и пустым набором;
- тексты RU/EN/KK/ZH;
- тесты: модульные (разбор `details` в строки для каждого типа поля), e2e (поле «Опасности» без набора: понятное сообщение, фокус на «Набор ответов», вкладка «Основное» отмечена), визуальные эталоны при изменении вида.

**Критерии готовности:**
- [ ] ни одно сохранение листа не показывает голое «Validation failed»;
- [ ] ошибка называет поле и ведёт к нему;
- [ ] аудит мест сохранения записан в PR;
- [ ] тесты, визуальные эталоны, CI зелёный;

## PR 455 — Подпись к изображению: выравнивание как в конструкторе

**Статус:** не начат
**Основание:** замечание 33.
**Цель:** выравнивание, выбранное для подписи изображения в конструкторе (слева, по центру, справа, по ширине), одинаково на плитке в предпросмотре, при прохождении, в кабинете ученика и в окне просмотра.
**Зависимости:** нет.

**Заметки по подготовке (по коду):**
- Выравнивание подписи уже сохраняется в разметке (`text-align` на `<p>`, PR 438); «слева» хранится как отсутствие выравнивания.
- `ChecklistPhotoStrip.tsx`: плитка рисует `RichText` внутри внешнего `<p>` (вложенные абзацы, выравнивание теряется), окно просмотра принудительно `textAlign: 'center'`.
- Установить воспроизведением, как выглядит подпись в поле конструктора по умолчанию (на скриншоте по центру без явного выбора) и привести к одному правилу.

**Что необходимо сделать:**
- плитка и окно просмотра выводят подпись блоком без вложенного `<p>` и без принудительного выравнивания: берётся то, что сохранено;
- подпись под плиткой занимает ширину своей картинки и переносится внутри неё;
- одно правило по умолчанию (без явного выбора): по центру (решение владельца 2026-11-09), одинаково в конструкторе, плитке и окне; так как «слева» сейчас хранится как отсутствие выравнивания (`sanitizeDescription` убирает `text-align:left`), для подписей изображений «слева» нужно хранить явно (общий очиститель должен сохранять `text-align:left` у подписи; проверить, что остальные поля не меняются), иначе выбор «слева» нельзя отличить от «не выбрано»;
- тесты: модульные (выравнивание из разметки доходит до плитки и окна), e2e (центр в конструкторе, центр в предпросмотре и при прохождении), визуальные эталоны.

**Критерии готовности:**
- [ ] выбранное выравнивание одинаково в конструкторе, предпросмотре, прохождении, кабинете ученика и окне просмотра;
- [ ] без явного выбора везде по центру, явный выбор «слева» сохраняется и показывается слева;
- [ ] тесты, визуальные эталоны, CI зелёный;
- [ ] проверка владельцем в его браузере.

## PR 457 — Правило пояснения у уровня шкалы

**Статус:** не начат
**Основание:** замечание 35.
**Цель:** при создании шкалы автор отмечает у каждого уровня, нужно ли пояснение («не нужно», «можно», «обязательно»); у всех критериев, использующих шкалу, поле пояснения появляется при этом ответе само, без настройки по одному критерию.
**Зависимости:** нет (опирается на PR 415).

**Заметки по подготовке (по коду):**
- Правило пояснения хранится у критерия (`noteRule`, `noteAnswers`, `noteRequired`; `checklist-item-note.ts` на сервере и `checklistItemNote.ts` в приложении, одно правило на обеих сторонах).
- Уровни шкалы живут в `checklist_scale_levels` (библиотека) и в `Checklist.scaleLevels` (шкала листа); нужны миграция (новое поле у уровня, по умолчанию «не нужно») и вывод в снимок сессии, чтобы начатые сессии сохраняли свою копию.
- Приоритет: правило самого критерия (если включено) главнее правила уровня; иначе действует правило уровня. Встроенную «Да/Нет» нельзя изменить, поэтому решить: поле у уровня «Нет» встроенной шкалы включается отдельной настройкой листа либо автор делает копию шкалы (рекомендация: копия, как для других шкал).
- Проверка на сервере: ответ с обязательным пояснением без пояснения не принимается (как сейчас у критериев).

**Что необходимо сделать:**
- миграция и контракты: у уровня шкалы «пояснение»: `off | optional | required`; API библиотеки шкал и шкалы листа, снимок сессии;
- редактор шкалы и редактор уровней листа: переключатель у каждого уровня; предпросмотр шкалы показывает пометку;
- единое правило на сервере и в приложении: пояснение предлагается и/или обязательно по правилу критерия, а при его отсутствии по правилу выбранного уровня; предпросмотр, прохождение, кабинет ученика;
- тексты RU/EN/KK/ZH; обновить документацию контрактов (docs-impact);
- тесты: модульные (приоритет критерий/уровень, обязательность), API-тесты (ответ «Нет» без пояснения отклоняется, «Да» принимается), e2e (шкала «Да/Нет»-копия с обязательным пояснением у «Нет»: при «Да» поля нет, при «Нет» есть и без него нельзя завершить), визуальные эталоны.

**Критерии готовности:**
- [ ] у уровня шкалы можно задать «не нужно / можно / обязательно»;
- [ ] у всех критериев с этой шкалой поле появляется по выбранному уровню, при «Да» его нет, при «Нет» оно обязательно;
- [ ] правило критерия, если оно включено, главнее; начатые сессии не меняются;
- [ ] тесты, визуальные эталоны, CI зелёный;
- [ ] проверка владельцем на листе «SLAM».
