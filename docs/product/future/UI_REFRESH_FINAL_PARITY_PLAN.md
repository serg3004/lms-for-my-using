# План финального выравнивания UI refresh с прототипами

## Контекст и результат анализа

План относится к двум утверждённым дизайн-референсам:

- `docs/lms-ui-prototypes-complete/admin/lms-admin-org-structure-refresh.html` — пять экранов
  организационной структуры и эталон shell приложения;
- `docs/lms-ui-prototypes-complete/admin/lms-checklist-sessions-refresh.html` — шесть экранов
  чек-листов и обучающих сессий.

Основная реализация из PR 309–323 уже находится в репозитории. Повторно реализовывать эти PR не нужно.

По текущему коду пять экранов организационной структуры соответствуют прототипу: реализованы общая
шапка, вкладки со счётчиками, карточная компоновка, адаптивные таблицы, обновлённое дерево
подразделений, локализованные импорт и история. Однако записи `admin-org-*` в
`docs/lms-ui-prototypes-complete/manifest.json` всё ещё содержат результат сравнения со старым SHA и
перечисляют уже устранённые расхождения.

Шесть экранов чек-листов имеют `parityStatus: aligned`. Сохраняются два сознательных отличия от
прототипа:

1. вкладка статуса «На паузе», потому что `paused` — реальное состояние сессии;
2. колонки «Баллы» и «Вес» в конструкторе, потому что эти значения участвуют в серверных расчётах.

Остаточные визуальные расхождения находятся на дашборде руководителя:

- на ширинах 768 и 1024 px четыре KPI-карточки раскладываются как `3 + 1`, а не ровной сеткой;
- индикаторы тренда используют `▲ / ▼ / ▬` вместо стрелок `↑ / ↓` из прототипа.

Работы разделены на два последовательных PR. PR 2 не должен начинаться до слияния PR 1, чтобы
финальная проверка и `lastComparedSha` относились к окончательной реализации.

## Общие ограничения

- Не менять бизнес-логику, API и расчёт аналитики.
- Не удалять существующие функции только потому, что они отсутствуют в прототипе.
- Не менять `apps/web/src/styles/tokens.css` и `defaultThemeSettings`.
- Тёмная тема HTML-просмотрщика не является частью production UI.
- Shell всех ролей сравнивать с `lms-admin-org-structure-refresh.html`; в остальных прототипах
  эталоном является только контентная часть.
- Не удалять два документированных сознательных отличия checklist UI.
- Для визуально значимых изменений обязательны `pnpm test:a11y` и `pnpm test:visual`.
- Visual baselines обновлять только через `.github/workflows/update-visual-baselines.yml` из ветки,
  содержащей актуальный `main`.
- Каждый изменённый PNG сравнить с предыдущей версией. Изменение постороннего экрана считать
  регрессией, а не принимать новым baseline.

## PR 1 — Финальное выравнивание адаптивного UI чек-листов

### Цель

Устранить оставшиеся визуальные расхождения страницы аналитики руководителя с прототипом на
промежуточных разрешениях, не меняя бизнес-логику, API и дизайн-токены.

### Что делаем

1. Исправляем сетку KPI в `ManagerChecklistsPage`:
   - четыре колонки на широком desktop;
   - две колонки на ширинах 768–1024 px;
   - одна или две читаемые колонки на mobile в зависимости от доступной ширины;
   - исключаем раскладку `3 + 1`.
2. Используем явные responsive breakpoints, а не подбор одного значения `minmax()`: единое значение
   не обеспечивает одновременно корректную раскладку на 768, 1024 и 1280 px.
3. Приводим индикаторы тренда к прототипу:
   - рост — `↑`;
   - снижение — `↓`;
   - отсутствие изменения — нейтральный символ;
   - для каждого состояния сохраняем доступное текстовое описание.
4. Сохраняем четыре KPI прототипа:
   - «Низкое выполнение»;
   - «Высокое выполнение»;
   - «Без сессий за период»;
   - «Средний результат».
5. Обновляем `ManagerChecklistsPage.spec.tsx`: проверяем четыре KPI, индикаторы тренда и их accessible
   names.
6. Проверяем visual matrix на ширинах 320, 375, 768, 1024, 1280 и 1440 px.
7. Если ожидаемое изменение превышает visual threshold, обновляем baselines только через workflow и
   просматриваем старые, новые и diff-изображения.
8. Проверяем документационное влияние. Если публичное поведение и контракты не изменились, фиксируем
   `reviewed-no-change` в PR согласно требованиям docs impact check.

### Зависимости

- Реализованный PR 316 — локализация чек-листов.
- Реализованный PR 321 — текущий дашборд руководителя.
- Ветка, содержащая актуальный `origin/main`.
- Рабочее окружение Playwright и возможность запуска workflow обновления visual baselines.

### Критерии готовности

- [ ] На 1280 и 1440 px четыре KPI расположены в одном ровном ряду.
- [ ] На 768 и 1024 px KPI расположены в сетке `2 × 2`.
- [ ] На 320 и 375 px отсутствуют горизонтальное переполнение, обрезанный текст и наложение карточек.
- [ ] На проверяемых ширинах отсутствует раскладка `3 + 1`.
- [ ] Индикаторы роста и снижения визуально соответствуют прототипу.
- [ ] Все индикаторы тренда имеют доступное текстовое описание.
- [ ] `ManagerChecklistsPage.spec.tsx` проходит.
- [ ] `pnpm test:a11y` проходит.
- [ ] `pnpm test:visual` проходит.
- [ ] Все изменённые PNG просмотрены; посторонние baselines не изменены.
- [ ] `apps/web/src/styles/tokens.css` и `defaultThemeSettings` не изменены.
- [ ] Повторный `pnpm agent:preflight` проходит перед завершением PR.

## PR 2 — Финальная parity-проверка и закрытие UI refresh

### Цель

Проверить обе группы production-страниц на итоговом SHA, актуализировать parity metadata и формально
закрыть план UI refresh.

### Что делаем

1. Подготавливаем репрезентативные тестовые данные:
   - оргструктуру с несколькими уровнями подразделений, кодами, должностями, требованиями,
     руководителями, группами и историей импорта;
   - checklist с группами критериев, контекстными полями и сессиями в запланированном, активном,
     приостановленном и завершённом состояниях;
   - пользователей ролей admin, instructor, learner и manager.
2. Сравниваем с `lms-admin-org-structure-refresh.html` пять production routes:
   - `/admin/departments`;
   - `/admin/positions`;
   - `/admin/position-courses`;
   - `/admin/groups`;
   - `/admin/org-structure-tools`.
3. На каждом экране оргструктуры проверяем shell, общую шапку, вкладки, счётчики, карточки, таблицы,
   состояния данных, доступные действия и mobile layout.
4. Сравниваем с `lms-checklist-sessions-refresh.html` шесть production flows:
   - `/admin/checklists`;
   - `/admin/checklists/sessions`;
   - `/admin/checklists/sessions/:id`;
   - `/instructor/checklists/sessions/:sessionId`;
   - `/learn/checklists`;
   - `/manager/checklists`.
5. На checklist-экранах проверяем шапки, вкладки, фильтры, таблицы, визард создания, конструктор,
   проведение сессии, контекстные поля, аналитику и отчёт.
6. Выполняем сравнение на desktop и mobile. Минимальный набор ширин: 375, 768, 1024 и 1440 px.
7. Если обнаружено фактическое расхождение:
   - сначала определяем, является ли оно регрессией или сознательным отличием;
   - регрессию исправляем в этом же PR;
   - сознательное отличие записываем в `knownDifferences` с технической или продуктовой причиной;
   - после исправления повторяем полную проверку затронутого экрана.
8. После фактического сравнения обновляем пять записей `admin-org-*` в
   `docs/lms-ui-prototypes-complete/manifest.json`:
   - `parityStatus: aligned`, если необъяснённых расхождений нет;
   - актуальные `lastComparedAt` и `lastComparedSha`;
   - удаление устаревших `knownDifferences`.
9. Обновляем шесть checklist-записей:
   - записываем актуальные `lastComparedAt` и `lastComparedSha`;
   - сохраняем только подтверждённые сознательные отличия;
   - не объявляем страницу `aligned`, если проверка выявила необъяснённое расхождение.
10. Актуализируем `docs/product/future/UI_REFRESH_IMPLEMENTATION_PLAN.md`:
    - общий статус — реализовано;
    - PR 309–323 — выполнены;
    - удаляем устаревшее утверждение, что оставшиеся PR не начаты;
    - отмечаем выполненные пункты Definition of Done;
    - фиксируем дату и SHA итоговой parity-проверки.
11. Запускаем проверки документации и подтверждаем отсутствие generated drift.

### Зависимости

- PR 1 смёржен.
- Все реализованные PR 309–323 присутствуют в рабочей ветке.
- Рабочие API, web-приложение и база данных.
- Тестовые пользователи ролей admin, instructor, learner и manager.
- Репрезентативные данные оргструктуры и checklist sessions.
- Ветка содержит актуальный `origin/main`.

- [ ] Фактически проверены все шесть checklist-экранов и flows.
- [ ] Каждый экран проверен минимум на mobile и desktop.

- [ ] В `knownDifferences` отсутствуют уже исправленные или неподтверждённые расхождения.
