### [2026-07-31] Redis rate limiting не развёрнут в проде — счётчики in-memory
**Файл:** `apps/api/src/modules/auth/`, инфраструктура Railway  
**Severity:** 🟡  
**[2026-08-06] Уточнение после перепроверки:** формулировка «не реализован» была неточной — код полностью готов: `createRedisRateLimitStore` (`apps/api/src/common/middleware/api-hardening.ts`) реализован, `main.ts` подключает его условно (`redis = apiEnv.REDIS_URL ? new Redis(...) : undefined`), `env.ts` требует `REDIS_URL` в production, если явно не выставлен `ALLOW_IN_MEMORY_RATE_LIMIT=true`.

Проблема не в коде, а в инфраструктуре: проверил через Railway MCP реальный прод-проект (`reasonable-reprieve` → сервис `api`) — сервиса Redis в проекте нет вообще, переменной `REDIS_URL` среди env vars сервиса `api` нет, а `ALLOW_IN_MEMORY_RATE_LIMIT` присутствует. То есть прямо сейчас в проде rate limiting реально работает в in-memory-режиме через явно включённый escape hatch — счётчики сбрасываются при рестарте, не синхронизированы при горизонтальном масштабировании.

**Что нужно сделать:** создать Redis-сервис на Railway в проекте `reasonable-reprieve`, прописать `REDIS_URL` для сервиса `api`, убрать `ALLOW_IN_MEMORY_RATE_LIMIT`. Это ops-задача, не задача на код.

### [2026-08-05] Сайдбар админки разъезжается на 2 колонки при зуме браузера 150%+ — причина не найдена
**Файл:** `apps/web/src/styles/admin.css` (`.admin-layout`, `.admin-sidebar`, `.admin-nav`), `apps/web/src/shared/adminPage.tsx`
**Severity:** 🟡
На проде (`web-production-b1f01.up.railway.app/admin/*`) при зуме браузера (Ctrl +/-, не сужении окна) от ~150% и выше пункты меню «Управление» и «Настройки» рисуются двумя колонками рядом вместо одного вертикального списка — при этом верхняя шапка остаётся десктопной (мобильный breakpoint не срабатывает). Подтверждено скриншотами пользователя на 250% зуме, воспроизводится стабильно, переживает жёсткую перезагрузку (Ctrl+Shift+R) — не кеш.

PR #492 (`fix(admin): contain horizontal overflow in admin layout at high browser zoom`) устранил горизонтальный скролл всей страницы при зуме, но **не** устранил именно это разъезжание на 2 колонки — это оказался отдельный, ещё не объяснённый симптом.

**Что уже проверено и исключено:**
- Деплой актуальный — подтверждено через Railway API, что на проде именно коммит из #492.
- Не кеш — воспроизводится после hard refresh.
- В `admin.css` нет `column-count`/`columns`/`flex-wrap`/`flex-direction: row`, которые могли бы объяснить раскладку в 2 колонки у `.admin-nav` (grep по всему файлу).
- 3 способа эмулировать зум Chrome в headless-браузере (сужение viewport, CSS `zoom`, CDP `Emulation.setPageScaleFactor`) не воспроизвели баг на локальной копии той же вёрстки/стилей — то есть либо баг специфичен для настоящего Ctrl+/- зума (не эмулируется программно так, как я пробовал), либо в игру вступает что-то, чего нет в упрощённой копии.
- Нет прямого сетевого доступа к живому URL из агентской песочницы (403), поэтому нельзя было сверить реально отданный CSS-бандл побайтово с локальным.

**Что нужно сделать, чтобы закрыть:**
1. Получить от пользователя скриншот панели DevTools → вкладка **Computed** для элемента `.admin-nav` в момент бага (250% зум) — это даст реальные computed-стили вместо гипотез.
2. Если `display`/`flex-direction` в Computed окажутся ожидаемыми (`flex`/`column`) несмотря на визуальный баг — проверить `.admin-sidebar`/`.admin-nav` на предмет **known Chromium-бага** с округлением/рендерингом flex-контейнеров при дробном zoom factor (баги такого рода фиксируются в Chromium bug tracker, обычно лечатся через `transform: translateZ(0)`/`will-change` форсирование отдельного composite-слоя, либо через `contain: layout`).
3. Проверить сценарий на другом браузере (Firefox/Safari) — если баг только в Chrome, это сильно сужает круг причин.
4. Проверить, не влияет ли `AccountSwitcher`/`LanguageSwitcher` (свои CSS-файлы, не входящие в `admin.css`) на layout сайдбара при зуме — не проверялось.

### [2026-08-05] E2E-тест «expired access cookie is refreshed» флейкует на CI → возможная причина найдена, проверяется на практике
**Файл:** `apps/e2e/tests/login-role-redirect.spec.ts:63`
**Severity:** 🟡
Тест падал по таймауту на CI 4 раза подряд с разной локацией фейла каждый раз (`refreshSucceeded`, потом дважды `expiredAccessRejected`) — признак таймингового флейка, а не детерминированного бага в коде. Два предыдущих расследования (`be8802f`, `e5cad53`) проверяли только код (`apiClient.ts`, `auth.controller.ts`, `auth.cookies.ts`) и признали его корректным — но не заглядывали в конфиг тестового харнесса.

**Найдено (2026-08-05, PR `claude/e2e-api-prod-build`):** `apps/e2e/playwright.config.ts` поднимал API для E2E через `pnpm --filter @lms/api dev` (`nest start --watch`) — dev-режим с live-компиляцией через ts-node/webpack и файловым watcher'ом, — хотя строчкой раньше уже собирался нормальный `dist/main.js`, который просто не использовался. В проде (`apps/api/Dockerfile`) сервер стартует иначе: `node dist/main.js`, без watcher'а. На CI-раннере (ограниченный CPU) watch-компилятор конкурирует за процессор с 2 параллельными Playwright-воркерами — именно у этого теста самый узкий тайминг-бюджет во всём наборе (3 последовательных round-trip'а подряд), поэтому он чувствительнее остальных к такой конкуренции.

**Фикс 1:** добавлен скрипт `apps/api/package.json` → `start:prod`: `node dist/main.js`; `playwright.config.ts` теперь запускает именно его вместо `nest start --watch` — тот же бинарник, что и в проде.

**Промежуточный результат:** следующий прогон на CI — прогресс, но не закрыто. Тест снова упал, но **на более поздних шагах** (`refreshSucceeded`/`retrySucceeded`, а не `expiredAccessRejected` как раньше), и весь набор из 20 тестов стал заметно быстрее (57.7s против прежних 1.2m) — подтверждает, что `dist/main.js` реально снял часть накладных расходов. Но общего 30-секундного лимита теста (Playwright default `test.setTimeout`) на 3 последовательных round-trip'а всё ещё впритык — этот лимит никогда раньше явно не поднимали (только внутренний `expect.poll` до 10с в `be8802f`, отдельно от общего таймаута теста).

**Фикс 2:** добавлен `test.setTimeout(60_000)` персонально для этого теста в `login-role-redirect.spec.ts` — не общий таймаут всего набора, только для теста с объективно самым узким тайминг-бюджетом.

**Статус:** оба фикса обоснованные и по отдельности подтверждённо помогают (быстрее сервер + больше времени именно там, где оно нужно), но 100% гарантии, что флейк не повторится, дать нельзя — CI-раннер с его ограничением CPU локально не воспроизвести. Считать закрытым только после нескольких зелёных прогонов `test:e2e` подряд без повторного падения этого теста. Если продолжит падать — см. пункты 2–3 из предыдущей версии этой записи (изоляция `--workers=1`, проверка event loop API) как следующий шаг.

### [2026-08-08] `Progress.createProgress` — нет unique-индекса, повторный вызов молча не обновляет статус → **закрыто (2026-08-08)**
**Файлы:** `apps/api/prisma/schema.prisma`, `apps/api/prisma/migrations/20260808150000_add_progress_unique_target/`, `apps/api/src/modules/progress/progress.service.ts`
При перепроверке §14 Progress (`ENTITY_TECHSPEC_IMPLEMENTED.md`) нашёл гэп серьёзнее исходной формулировки. На `Progress` не было `@@unique([courseId, lessonId, userId])`: `createProgress` делал `findFirst` → `create` без транзакции — не атомарно (race condition, возможны дубли строк при параллельных запросах), и если запись уже существовала, повторный `POST /progress` с другим `status` молча возвращал старую запись без изменений — `PATCH /progress` не существует, обновить прогресс было в принципе невозможно после первого вызова. На фронтенде `POST /progress` при этом нигде не вызывается (`apps/web/src/shared/api/progress.ts` — только чтение), риск был 100% недостижим через UI сегодня, но инфраструктура для «отметить урок пройденным» была явно неполной для будущего использования.
Исправлено: добавлен `@@unique([courseId, lessonId, userId])` (миграция с дедупликацией существующих дублей перед созданием индекса), `createProgress` для случая с `lessonId` теперь `upsert` по этому ключу. Для курсового прогресса без `lessonId` unique-индекс не покрывает случай (Postgres считает `NULL` различными значениями) — остался `find-then-write`, но теперь тоже обновляет статус вместо игнорирования.

Утверждение было неточным. `createSensitiveRouteRateLimitMiddleware` (`apps/api/src/common/middleware/api-hardening.ts`) уже вызывает тот же самый `createApiErrorResponse(...)` (`apps/api/src/common/api-response.ts`), что использует `ApiExceptionFilter` для всех остальных ошибок API — с момента создания файла (коммит `5ffc780`, 2026-08-03, до этой записи concern). Структура JSON от этого не меняется.

### [2026-07-31] Fail-open при недоступном Redis — rate limit полностью отключается → **закрыто, при перепроверке не подтвердилось (2026-08-06)**
Утверждение было неверным. Проверил `apps/api/src/common/middleware/api-hardening.ts`: при ошибке `resolvedStore.increment` (случай реального сбоя Redis) код не пропускает запрос — переключается на `fallbackStore` (тот же in-memory лимитер, что и при полном отсутствии Redis) и продолжает считать лимиты, `429` по-прежнему возвращается. Поведение соответствует описанию в `docs/RATE_LIMIT_FAILURE_POLICY.md` («Local emergency limiter with the same limits»), а не «полностью отключается».
