**Тип:** EVIDENCE, срез кода и решений от 2026-10-27.

**Канонические владельцы:** `apps/api/src/modules/auth/roles.ts`, guards, `ChecklistsController`, `ChecklistReviewAccessService`, сервисы событий/уведомлений. Актуальный статический инвентарь выводится в [generated/RBAC](../generated/RBAC.md); эта таблица — датированная сверка, а не новый источник прав.

## Доступность исходной матрицы

В [плане PR 349](../product/future/CHECKLIST_WORKPLACE_TRAINING_PARITY_PLAN.md) названы 13 направлений проверки. Исходная таблица «Роли и права» с отметками по ролям в доступных материалах не найдена. Общий HTML-прототип страницы ролей содержит карточки ролей, но не эту матрицу. Поэтому совпадение с исходными отметками **не подтверждено**.

Первые семь направлений ниже взяты из плана. Три группы уведомлений и три группы отчётов — рабочая группировка фактических механизмов LMS: точные названия/порядок соответствующих строк оригинала не установлены. Они не выдаются за восстановленную матрицу прототипа. Изменение прав по отсутствующим отметкам не выполняется.

## Проверенный дефект object scope

В исходном коде назначенный наблюдатель и роль пользователя проверялись отдельно, но `sessionScope()` давал manager+instructor объединение «команда или назначенные мне сессии». Контроллер использовал его также для start/pause/resume/complete, обратной связи, контекста и геопозиции. Один лишь `overrideReason` позволял такому пользователю записать геопозицию от имени другого наблюдателя.

Воспроизведение на изолированном PostgreSQL: семь отрицательных сценариев разрешались вместо 404; ещё один сценарий возвращал кешированный ответ чужой conduct-операции. Положительный сценарий собственного проведения, командной отмены и admin override проходил. Это расхождение с уже документированным разграничением действий, а не вывод о неизвестных отметках прототипа.

Исправление PR 349 использует существующий `observerActionScope()` для conduct, feedback, context и записи location. Чтение и планирование сохраняют свои области. Идемпотентный transition возвращает старый результат только после проверки текущего object scope; ключ другой сессии даёт 409.

Проверки закреплены в `checklist-session-observer-create.database.spec.ts`, `checklist-session.service.spec.ts` и `roles.spec.ts`. Существующие cross-tenant, manager team и multi-role проверки остаются обязательными; результаты проверки исправления относятся к версии PR, а не к исходному SHA этой таблицы.

## Дополнительная проверка идемпотентности

Полный PostgreSQL-прогон обнаружил прежнюю гонку одновременного создания с одним ключом (тест уведомлений PR 345): PostgreSQL иногда возвращает unique violation вместо serialization failure, и второй запрос получал 409. Детерминированный unit-сценарий воспроизвёл тот же отказ. Исправление перечитывает сохранённый ответ после unique conflict только для совпадающих instance/observer/key в той же организации, без повторных событий и аудита. Предварительная проверка области участника сохраняется; чужой ключ не даёт ответ.

DEC-CHKS-004 принято владельцем 2026-10-27: индивидуальные наборы прав нужны, реализация общей модели выносится отдельно. [План модели](../product/future/CUSTOM_ROLE_PERMISSIONS_PLAN.md) описывает каталог действий/областей, совместимость системных ролей, хранение, отзыв, guards, административный UI и этапы включения.

Для завершения именно сравнения с прототипом требуется первичная таблица с отметками по ролям либо отдельное решение владельца принять текущую проверенную матрицу как новый продуктовый baseline. Решение о необходимости индивидуальных прав само по себе таким подтверждением не является.
