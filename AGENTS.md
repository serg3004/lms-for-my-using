# Правила работы ИИ-агентов

Этот файл задаёт общий процесс для Codex, Claude и других ИИ-агентов, работающих с репозиторием. Специализированные инструкции могут дополнять эти правила, но не должны ослаблять проверки ниже.

## Documentation Rules

1. Карта документации и правила ownership находятся в `docs/README.md`.
2. Читать только task-relevant docs; не обходить весь `docs/` без необходимости.
3. Current implementation fact проверять по canonical owner-source, указанному в `docs/README.md`.
4. Archive, historical и evidence не использовать как authority для current поведения без повторной проверки.
5. При изменении behaviour, API, schema, RBAC, config, env, deploy/migration procedure или user workflow проверить связанную документацию в том же PR.
6. Не создавать ручной inventory, если факт надёжно выводится из code/runtime source.
7. Snapshot/live facts привязывать к дате, SHA или environment; не выдавать их за вечную current truth.
8. Не копировать сюда roles, endpoints, module topology и другие domain inventories; хранить здесь только процесс.

## Перед началом задачи

1. Начинать работу только от актуального `origin/main` в отдельной ветке.
2. Выполнить `pnpm agent:preflight` до изменения кода и повторить перед финальной проверкой.
3. Проверить, не реализована ли задача уже в `main`, открытом или недавно слитом Pull Request.
4. Прочитать связанные `README`, тесты, конфигурацию, CI и документацию до изменения поведения.
5. Не работать напрямую в `main`, `master` или `develop`.

## GitHub task identity

Для одной пользовательской задачи или одного этапа плана действует неизменяемая GitHub identity:

**1 task → 1 remote branch → 1 Pull Request.**

1. Перед созданием ветки MUST проверить существующие remote branches и Pull Requests задачи.
2. Если рабочая ветка задачи уже существует, MUST продолжать работу только в ней.
3. Если Pull Request задачи уже существует, MUST продолжать работу только в нём.
4. После первого push MUST NOT создавать вторую remote branch для той же задачи.
5. После создания Pull Request MUST NOT создавать replacement branch или replacement Pull Request.
6. Любые ошибки реализации, тестов, CI, документации, merge conflict или review feedback MUST исправляться в той же рабочей ветке и том же Pull Request.
7. Corrective commits после открытия Pull Request разрешены и предпочтительнее пересоздания ветки или PR.
8. MUST NOT пересоздавать branch/PR ради одного коммита, squash или «чистой» истории, исправления CI/тестов/документации либо cosmetic cleanup.
9. MUST NOT закрывать рабочий Pull Request, если задачу технически можно продолжить в нём.
10. Требование «один логический коммит» применяется только до первого push. После первого push приоритет имеет сохранение одной task branch и одного Pull Request.
11. Новая branch или новый Pull Request для той же задачи допускаются только после явного разрешения пользователя.
12. Если продолжение существующей branch/PR технически невозможно, MUST остановиться, показать точную причину и запросить разрешение пользователя на replacement.

## Перед исправлением CI

1. Прочитать точное имя упавшего job/step и текст ошибки.
2. Сначала исключить устаревшую ветку: рабочая ветка должна содержать текущий `origin/main`.
3. Классифицировать проблему как код, тест, visual regression, окружение или устаревшая ветка.
4. Не обновлять visual snapshots, пока не доказано, что отличие ожидаемое, а ветка актуальна относительно `main`.
5. Для одной и той же ошибки выполнять не более трёх обоснованных циклов `причина → изменение → повторная проверка`.

## UI и visual regression

Изменения в shared UI, layout, navigation, design tokens и глобальных стилях считаются визуально значимыми.

Для таких изменений обязательно:

1. Запустить релевантные unit/integration проверки, `pnpm test:a11y` при изменении accessibility и `pnpm test:visual` для визуально значимого UI.
2. При падении screenshot-тестов изучить expected/actual/diff artifacts и определить, является ли отличие регрессией или ожидаемым изменением.
3. Обновлять baselines только через `.github/workflows/update-visual-baselines.yml` и только из ветки, содержащей текущий `main`.
4. Просмотреть изменённые PNG перед коммитом/merge.
5. Не отмечать задачу или документацию как выполненную, пока обязательные проверки не зелёные либо явно не зафиксированы как непроверенные с причиной.

## Перед Pull Request

1. Повторить `pnpm agent:preflight`.
2. Проверить итоговый diff и отсутствие секретов/лишних файлов.
3. Запустить обязательные для затронутой области проверки.
4. Убедиться, что для той же задачи не существует активного PR.
5. До первого push сформировать один логический коммит, если это практически возможно. После первого push любые исправления MUST выполняться corrective commits в той же branch и том же Pull Request.

## Запрещено

- прямой push в защищённую ветку;
- `git push --force`;
- создание второй task branch или replacement Pull Request для уже существующей задачи без явного разрешения пользователя;
- обновление snapshot/baseline только ради зелёного CI без проверки diff;
- отключение тестов, линтера или required checks ради прохождения CI;
- объявление задачи завершённой при красных обязательных проверках.
